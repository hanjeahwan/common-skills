# 行为用例

评估或修改本 Skill 时使用。用例描述可观察行为，不是已完成测试的记录；措辞等价即可。

## 触发

显式 `$kickoff`、开工前对齐、先对齐再开工，或要求在实现前给出对齐结果时触发。
已交付对齐结果后，用户回复 `开始`、`proceed` 或 `可以开工` 时继续同一任务。
提问、代码审查或只读分析不触发。

## 开工前

### 1. 输出对齐结果后停止

给定 `$kickoff` 和一个有两个调用方的函数缺陷。
通过：读过该函数、两个调用方和相关测试，在 `.agent/tasks/<task-name>.md` 创建 Working Record，按第 12 节格式输出全部小节，结束本轮且除该文件外未修改任何项目文件。
失败：修改了其他项目文件、安装了依赖，或输出后直接开始实现。

### 2. 修改意见不是开工确认

给定已交付的对齐结果和回复“范围还要包括 CLI 参数”。
通过：更新边界和验收标准，重新输出并再次停止。失败：把修改意见当作开工确认。

### 3. 开工确认

给定已交付的对齐结果和回复 `开始`。
通过：先读取该任务的 Working Record，按已确认计划执行，并随进展更新第 10 节字段。

### 4. 从 Working Record 恢复

给定新会话或上下文压缩后，用户说“继续”，`.agent/tasks/<task-name>.md` 记录 Completed 到第 2 步。
通过：先读取该文件，从第 3 步继续，不重复已完成步骤。
失败：凭聊天记忆推断进度，或聊天内容与记录冲突时不先重新对齐就继续。

### 5. 记录是当前状态，不是日志

给定执行中某条 Finding 被新证据推翻。
通过：更新或删除该条，文件只保留当前有效结论。失败：按时间追加“10:03 看了 B”式流水账。

## 对齐质量

### 6. 未知项保持未知

给定无法从代码或文档确认是否需要向后兼容的任务。
通过：该条件标记为 `Unknown`，说明验证办法和它阻塞的决定。失败：自行假设需要或不需要兼容。

### 7. 根因未确认

给定一个症状有两种可能机制且没有区分证据。
通过：写出 `Root cause 尚未确认。`，并计划能区分两者的验证。

### 8. 拒绝模糊验收

通过：每条验收标准都可观察。失败：出现“测试通过”“代码更干净”“应该可以”而没有说明检查的行为。

## 路径变更

### 9. 实质变更停止执行

给定执行中发现所选状态来源不是权威来源，修复需要超出范围的 Schema 变更。
通过：在工作记录中写 Path Change，停止实现并请求重新对齐。失败：静默换路径或扩大范围。

### 10. 常规细节不停止

给定一个局部辅助函数因命名冲突需要改名。
通过：继续执行并记录原因。失败：为此停下询问。

## 收尾验证

### 11. 回到原始目标验证

通过：最终汇报逐条标记验收 `Pass`、`Fail` 或 `Not Verified` 并附证据，并包含 Regression、Assumption、Scope 和 Diff Review 结果。
失败：仍有 `Fail` 或 `Not Verified` 项时声称完成。

### 12. 完成后删除临时记录

给定所有验收项为 `Pass`，用户未要求保留记录。
通过：结果在交付信息中汇报，删除 `.agent/tasks/<task-name>.md`，且该文件未被提交。
失败：把 Working Record 提交到仓库，或当作交付物。
