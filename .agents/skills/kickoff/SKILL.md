# Agent 开工前对齐模板

在开始任何实质性实现、修改、重构、迁移或批量操作之前，先完成以下对齐。

目标不是快速进入编码，而是确保：

* 我们解决的是同一个问题；
* 目标、边界和验收标准足够具体；
* 当前系统背景已经调查；
* 已知事实、推断和未知项被区分；
* 执行路径已经明确；
* 后续路径变化有依据；
* 工作过程可以持续追踪；
* 最终可以回到原始目标验证结果。

在我明确确认“开始 / proceed / 可以开工”之前，不执行实质性修改。

---

# 1. Goal — 我们真正要解决什么

不要只复述我最初的一句话。

结合当前上下文，把目标展开成具体的业务和技术结果。

请回答：

### 原始目标

> 用 1–3 句话描述我提出的问题。

### 你理解的真实目标

说明：

* 最终希望发生什么变化；
* 谁会受到影响；
* 什么行为需要改变；
* 什么行为必须保持不变；
* 这个任务为什么存在。

### 必须始终成立的条件

列出完成任务过程中不能被破坏的不变量。

例如：

* 数据一致性；
* 权限边界；
* API 契约；
* 金额正确性；
* 向后兼容；
* 单一真源；
* 用户已有行为。

如果这些条件目前无法确认，标记为 `Unknown`，不要自行假设。

---

# 2. Acceptance — 怎样才算完成

把目标转化为可验证的结果。

### 完成标准

列出具体、可观察、可验证的验收条件：

* [ ] 行为 A……
* [ ] 行为 B……
* [ ] 边界情况……
* [ ] 原有行为……
* [ ] 必要检查……

不要用以下模糊标准代替验收：

* “代码更干净”
* “架构更合理”
* “应该可以”
* “大概解决了”
* “测试通过”

测试只是验证手段，不是业务目标本身。

### 明确的失败条件

什么情况下即使实现完成，也应该判断任务失败？

---

# 3. Scope — 边界在哪里

### In Scope

本次任务允许涉及：

* …
* …
* …

### Out of Scope

本次明确不处理：

* …
* …
* …

### 修改权限

说明预计是否需要修改：

| 类型            | 是否需要 | 说明 |
| ------------- | ---- | -- |
| 业务逻辑          |      |    |
| 公共 API        |      |    |
| 数据结构 / Schema |      |    |
| 数据迁移          |      |    |
| 配置            |      |    |
| 依赖            |      |    |
| 测试            |      |    |
| 文档            |      |    |
| UI / 文案       |      |    |
| 外部系统          |      |    |

如果某项修改会明显扩大兼容性、成本、风险或不可逆影响，必须在这里暴露。

---

# 4. Context — 当前系统实际上是什么状态

在提出方案之前，先调查相关上下文。

至少检查与任务直接相关的：

* 当前实现；
* 调用链；
* 调用方；
* 数据流；
* 状态来源；
* 配置；
* 类型定义；
* 相关测试；
* 文档；
* 依赖和版本；
* 已存在的工作区修改。

必要时再检查：

* Git 历史；
* Issue / PR；
* 外部 API 文档；
* 对应版本的官方文档；
* 生产约束或历史数据。

### 当前链路

用尽量简单的方式描述：

```text
输入
  ↓
组件 / 模块 A
  ↓
组件 / 模块 B
  ↓
状态 / 数据
  ↓
输出
```

如果状态存在多个来源，明确指出：

```text
事实 X
├─ 来源 A
└─ 来源 B
```

并判断哪个应该是权威来源。

### 已发现的问题

只列有证据的问题。

每个问题说明：

**问题：**

**证据：**

**触发条件：**

**实际后果：**

不要因为代码“看起来不好”就自动把它定义成缺陷。

# 5. Facts / Assumptions / Unknowns — 不要把推断当事实

把关键信息分成三类。

## Confirmed Facts

已经从代码、数据、文档或其他可靠来源确认：

* …
* …

## Current Assumptions

目前合理，但尚未完全验证：

* …
* …

说明每个假设如果错误，会影响什么。

## Unknowns

仍然未知：

* …
* …

对于每个重要 Unknown，说明：

1. 能否自行调查；
2. 如何验证；
3. 如果无法验证，会影响什么决定。

优先通过调查消除 Unknown。

不要为了“快速推进”偷偷把 Unknown 转换成 Assumption。

---

# 6. Root Cause — 为什么会出现这个问题

不要直接从症状跳到解决方案。

描述：

```text
表面症状
   ↓
直接失效机制
   ↓
为什么该机制会发生
   ↓
真正应该归属规则的位置
```

区分：

* 根因；
* 次生影响；
* 历史遗留；
* 与本任务无关的问题。

如果目前证据不足以确认根因，明确写：

> Root cause 尚未确认。

不要伪造确定性。

---

# 7. Path — 建议采用什么解决路径

基于前面的目标、约束和调查，提出一个**最小充分方案**。

### 推荐路径

说明：

1. 改什么；
2. 不改什么；
3. 规则最终归属在哪里；
4. 数据 / 状态的权威来源是什么；
5. 调用链会如何变化；
6. 为什么这是解决根因的最小方案。

### Before

```text
当前：
A
 ↓
B
 ↓
C
```

### After

```text
修改后：
A
 ↓
D
 ↓
C
```

### 为什么不选择其他明显方案

只讨论真正有竞争力的方案。

例如：

**方案 B**

不采用，因为：

* 会产生双写；
* 需要长期同步；
* 扩大接口；
* 只是掩盖异常状态；
* 解决的是症状而不是根因。

不要为了显得完整机械列出大量备选方案。

---

# 8. Change Control — 什么情况下允许改变路径

完成对齐后，默认沿已确认路径执行。

不要因为：

* 某段代码难改；
* 遇到第一个报错；
* 出现一个更“优雅”的想法；
* 发现可以顺便重构；
* 另一个方案代码更少；

就自行改变方向。

只有出现新的证据，证明当前路径：

* 无法满足 Goal；
* 无法满足 Acceptance；
* 违反重要 Constraint；
* 基于错误假设；
* 会破坏系统不变量；
* 技术上不可行；

才允许调整路径。

调整前记录：

## Path Change

**原路径：**

**新发现：**

**为什么原路径不成立：**

**建议的新路径：**

**对 Scope / Acceptance / Risk 的影响：**

如果变化实质影响行为、兼容性、范围、成本或不可逆结果，停止实现并重新与我对齐。

如果只是局部、常规、可逆的实现细节，可自行调整并记录原因。

---

# 9. Execution Plan — 开工后按什么顺序做

计划保持短小，只包含可以检查完成状态的步骤。

例如：

1. [ ] 修正权威状态来源
2. [ ] 调整相关调用链
3. [ ] 清理旧路径
4. [ ] 验证关键场景
5. [ ] 检查是否存在遗漏调用方
6. [ ] 最终回到 Acceptance 验证

每一步应该对应一个明确结果，而不是：

* “研究一下”
* “优化代码”
* “处理问题”

---

# 10. Working Record — 工作文件持续更新

每个任务维护一个独立的 Working Record。

默认路径：

```text
.agent/tasks/<task-name>.md
```

开始调查时创建，整个任务期间持续维护。

开始或恢复任务时，Agent 必须先读取该文件，再继续工作。

Working Record 是当前任务的临时执行状态，不是项目正式文档，也不是最终交付物。

Working Record 是任务状态的单一真源。聊天上下文用于沟通，Working Record 用于恢复任务状态；两者冲突时，应先重新对齐并更新 Working Record。

至少包含：

## Goal

当前确认的目标。

## Acceptance

当前确认的验收条件。

## Current Plan

当前已确认的执行路径。

## Completed

已经完成的计划项。

## Findings

执行过程中发现、且会影响判断的新事实。

## Decisions

已经做出的重要决策及依据。

## Path Changes

执行路径发生变化时，记录：

* 原路径
* 新证据
* 修改原因
* 新路径

## Remaining Unknowns

尚未解决、且仍可能影响结果的问题。

更新规则：

1. Goal、Acceptance 或 Plan 变化时立即更新。
2. 得到会影响方案的新事实时更新 Findings。
3. 做出重要取舍时更新 Decisions。
4. 完成计划步骤时更新 Completed。
5. 不记录命令执行、文件浏览等无价值流水账。
6. 文件内容代表“当前有效状态”，过时内容应更新或删除，而不是无限追加历史记录。

任务完成后：

* 最终结果在正常交付信息中汇报；
* Working Record 默认作为临时文件删除；
* 除非用户明确要求保留，不将其提交到仓库。

# 11. Verification — 最后不是看“代码写完没有”

实现完成后，重新从最初目标验证。

不要只验证最后修改的函数。

### Acceptance Check

逐条验证：

* [ ] Acceptance 1 — Pass / Fail / Not Verified
* [ ] Acceptance 2 — Pass / Fail / Not Verified
* [ ] Acceptance 3 — Pass / Fail / Not Verified

### Regression Check

确认关键原有行为是否保持。

### Assumption Check

回看最初的 Assumptions：

* 哪些已经被验证；
* 哪些仍然是假设；
* 是否有假设被证明错误。

### Scope Check

确认没有因为执行过程无意扩大修改范围。

### Diff Review

从反例和失败场景检查最终修改：

* 是否只修了正常路径；
* 是否引入新的多源状态；
* 是否存在隐藏 fallback；
* 是否吞掉异常；
* 是否破坏兼容性；
* 是否产生重复规则；
* 是否留下已经失效的旧路径。

# 执行阶段原则

开始执行后：

1. 始终以 Goal 和 Acceptance 为最高依据。
2. 当前 Plan 是默认执行路径，不随意漂移。
3. 新证据优先于原计划。
4. 不为了通过测试保留错误设计。
5. 不用 fallback、判空、重试或默认值掩盖内部不变量问题。
6. 不进行与目标无关的重构。
7. 不重复维护同一事实的多个权威来源。
8. 保留已有用户修改。
9. 工作记录随着事实和决策更新。
10. 完成时必须重新按照 Acceptance 做闭环验证，而不是根据“改了多少代码”判断完成。
